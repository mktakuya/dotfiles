# デプロイ可能なインクリメントへ分解する

利用者または運用者が確認できる振る舞いを軸に、入口から出口まで通るチケットを設計する。チケットが 1 枚で済む場合も、複数へ分解する場合も同じ軸で切る。実装担当者が各チケットだけで実装・検証範囲を判断できる形にする。本スキルでは実装やデプロイ自体は行わない。

## 開始条件と依頼の範囲

- 共通 AGENTS.md の BFS → DFS に従い、解決方針が選択された後の DFS フェーズで使う。ただし解決方針が実質一択の機能追加や、既存の仕組みをなぞる実装では BFS を省略してよい。複数のアーキテクチャや解決方針が競合したまま未決定なら、先に BFS と意思決定を行い、決定まで詳細なチケット化も外部への書き込みも進めない。
- チケットが 1 枚で済むなら分解はしないが、動作可能の不変条件と共通 Issue フォーマットは同じく適用する。依存関係や置き換え順序など該当しない項目は飛ばす。
- 設計や組み替えの提案だけを求められているなら、共通フォーマットの案と依存関係を提示して終了する。外部サービスへの書き込み権限は推測しない。
- チケットの作成または更新が依頼されていれば、設計とセルフレビューの後、依頼された範囲の書き込みと再取得による確認まで行う。既に明確な依頼があれば、儀式的な再承認は求めない。
- 既存チケットの削除・クローズは、明示的な依頼なしに行わない。

## 1. ツール非依存でインクリメントを設計する

仕様、既存チケット、対象リポジトリの規約と現状を読み、提供済みの経路、選択済みの方針、対象環境、制約を把握する。不明な環境や検証経路を合意済みと扱わず、設計上の仮定を明示し、受け入れ条件を左右する不明点は確認する。

### 動作可能の不変条件

各 Issue のマージ時点で、次のすべてを満たす設計にする。

- そのコミットを対象環境へデプロイできる。master/main を常にデプロイ可能に保つ。
- 既に提供済みの利用可能な経路が壊れていない。
- 新しいインクリメントに、その時点で確認可能な経路がある。

Issue の完了条件には、原則として本番または合意した本番相当環境へ実際にデプロイし、新しいインクリメントを確認することを含める。ローカルテストや CI 成功だけで代替しない。一般公開できない場合は feature flag、限定ユーザー、専用 URL、手動操作など、誰がどの経路で確認できるかを書く。例外が必要なら理由と代替検証を示し、合意なく完了条件を弱めない。

### 境界と順序

- 最初のインクリメントは、入口から出口まで通る最小の walking skeleton にする。必要なコード、インフラ、CI、デプロイ、環境設定、ログなどの観測手段をこのインクリメントに含める。既存の仕組みは再利用する。
- 未実装部分はスタブ、固定レスポンス、手動操作、feature flag で代替してよい。flag をオフにするだけでは新しいインクリメントの確認にならないため、限定的にオンにして通せる経路も用意する。
- 後続チケットで仮実装を段階的に本物へ置き換える。各置き換えも独立した確認経路を持ち、必要な環境変更や観測手段を同じインクリメントに含める。
- UI、バックエンド、インフラといった技術レイヤーだけでは分割しない。最終 E2E チケットを初回の結合確認や実環境確認にしない。
- 依存は実際に必要な先行インクリメントだけに付ける。独立した置き換えを不要に直列化しない。「独立して検証可能」は先行 Issue がマージ済みの状態で検証できることであり、後続 Issue の完了は要求しない。

### 準備 Issue の例外

単独で利用価値を増やさない準備 Issue は原則作らない。安全な移行、後方互換性、作業順序の制約などから独立させる方が明らかに合理的な場合に限り、次のすべてを満たせば許容する。

- 単体で安全にマージ、デプロイ、検証できる。
- 既存の利用可能な経路を壊さない。
- 対象環境で何を確認すれば準備が正常と判断できるか明記する。
- その準備を利用する後続 Issue を特定する。
- 縦切りへ含めるより独立させる方が合理的な理由を説明する。

例えば、既存経路と互換性を保つスキーマの追加を先行させる場合は、適用・互換性の検証と利用する後続 Issue を示す。準備が先行しても、最初の機能インクリメントは walking skeleton にする。

### 共通 Issue フォーマット

サービスの書式へ変換する前に、仮 ID を付けた以下の共通形式で整理する。核となる目的、新しい振る舞い、確認経路、対象環境と確認方法、受け入れ条件は具体化する。他の項目は対象に必要なものだけを選び、空欄を機械的に並べない。

```markdown
### 仮 ID — タイトル（確認できる振る舞い）
- 目的:
- マージ後に新しく何が動くか:
- 利用者または運用者が通せる経路:
- 対象環境とそこでの確認方法（操作・期待結果・観測手段）:
- まだスタブまたは仮実装の境界:
- コード・インフラ・CI・デプロイへの影響:
- feature flag またはロールバック方法:
- 独立して検証可能な受け入れ条件:
- 先行 Issue への依存:
- 後続 Issue で置き換える仮実装:
- 準備 Issue の場合、独立させる理由と利用する後続 Issue:
```

列全体の順序と依存も示す。例として、申請機能なら「限定 URL から申請し固定レスポンスを受け、対象環境のログで到達を確認」→「申請を永続化して結果を確認」→「手動の後続処理を自動化して完了を確認」のように、毎段階で通せる経路を残す。これは固定のチケット数や構成ではなく、対象の利用価値に合わせる。

## 2. チケット列をセルフレビューする

書き込み前に、先行 Issue だけがマージ済みの状態を順に想定して確認する。1 枚で済むチケットでは、複数チケットを前提とする項目を飛ばしてよい。

- 各 Issue 単体で安全にマージ・デプロイでき、各マージ後も既存の利用可能な経路が残るか。
- 新しいインクリメントを対象環境で確認でき、後続 Issue 待ちの検証になっていないか。
- 技術レイヤーだけの横切りを避け、最初の機能インクリメントが walking skeleton になっているか。
- CI、デプロイ、環境設定、観測手段を最後へ先送りしていないか。
- 最終 Issue が初回の結合確認または実環境確認になっていないか。
- 仮実装の置き換え順序と担当する後続 Issue が明確か。
- 必要な feature flag やロールバック方法が欠けていないか。
- 準備 Issue が例外条件をすべて満たすか。
- 依存関係に循環や不要な直列化がないか。

満たさない場合は説明の追記だけで済ませず、Issue 境界、順序、依存関係を組み直し、再レビューする。

## 3–5. 書き込み先決定・サービスへの反映・再取得

チケットの作成または更新が依頼されている場合のみ、[書き込み手順](references/publishing.md) を読み、書き込み先の決定、サービス形式への変換と反映、結果の再取得を行う。
