# チケットへの反映

分解とセルフレビューを終え、ユーザーがチケットの作成または更新を依頼している場合にだけ実行する。

## 3. 書き込み先を決定する

次の優先順位でサービスと対象を決める。

1. ユーザーが明示したサービス、リポジトリ、Jira プロジェクト。
2. 渡された GitHub URL、Jira URL、Issue 番号、Jira チケット ID。
3. 現在のリポジトリや会話から一意に判断できる対象。
4. 一意に判断できなければ、書き込み前にユーザーへ確認する。

Issue 番号だけでリポジトリを推測しない。参照元のチケットと書き込み先は異なり得るため、明示された書き込み先を優先する。明示的な依頼なしに GitHub と Jira の両方へ同時に作成しない。

## 4. サービスの形式と規約に合わせて作成・更新する

対象プロジェクトの AGENTS.md、テンプレート、既存チケットの書式を確認し、共通フォーマットの意味を保って本文へ変換する。実際に書き込む本文を先に整理する。既存チケットを更新する場合は、作成と更新の別と仮 ID との対応も併せて整理する。

### サービス別の委譲

| 対象 | 利用する規約・手順 |
| --- | --- |
| GitHub Issues | 共通 AGENTS.md のとおり `gh` を使う。対象リポジトリの Issue template（`.github/ISSUE_TEMPLATE/` など）、必須項目、既存の書式を確認する。Issue 専用の既存スキルがあれば利用し、なければ `gh issue` の該当操作の `--help` で確認する。複数行の本文はファイルで渡す。 |
| Jira | [read-jira-workitem](../../read-jira-workitem/SKILL.md) に従い `acli` で取得・作成する。対象プロジェクトの issue type、必須フィールド、既存の書式を確認する。description の更新は [update-jira-workitem](../../update-jira-workitem/SKILL.md) に委譲し、ADF の構造と既存の書式を保持する。 |
| 既存コンテンツの更新（両サービス） | [external-service-edit](../../external-service-edit/SKILL.md) を読み、更新直前の再取得、差分確認、必要なバックアップを行う。GitHub では `gh` で同じ原則を適用する。 |

PR 作成や stacked PR のスキルを Issue 操作の代わりに使わない。API のペイロードやサービス固有の操作詳細はここへ複製せず、既存スキル、プロジェクト規約、利用中の CLI のヘルプで確認する。

### 反映の順序

チケットが 1 枚なら、依存関係の項目は飛ばしてよい。

- 先行 Issue から依存関係が分かる順序で作成し、仮 ID と取得した Issue 番号 / Jira キー / URL の対応表を保持する。
- 実 ID を使い、後続 Issue の依存先と先行 Issue の仮実装を置き換える後続先を反映する。全件作成後に必要な相互参照を追記する。
- 利用可能な依存関係機能があればプロジェクト規約に合わせる。対応しない表現は本文中のリンクで明示し、親子関係を依存関係と混同しない。

### 既存チケットを更新する場合

新規作成だけなら読み飛ばす。既存チケットの本文を書き換えるとき、または作成後に既存チケットへ参照を追記するときに適用する。

- 更新直前に最新版を再取得する。ペイロード準備など別のツール呼び出しを挟んだら再取得し直す。準備時の内容から変更されていれば更新を止め、`external-service-edit` に従ってユーザーに確認する。
- 変更されていなくても既存の説明や無関係な項目を保ち、依頼された変更だけを適用する。破壊的な置換は元の内容をローカルに保存する。

### 部分失敗と再試行

作成・更新ごとに結果と実 ID を記録する。タイムアウトなどで成功が不明なら、再取得・検索で結果を確認するまで同じ作成を再試行しない。重複の可能性を解消できない、権限や必須情報が不足する、ユーザー変更と競合する場合は該当操作を止める。

失敗した先行 Issue に依存する書き込みも止め、成功した対象を維持する。依頼範囲で独立して進められる対象は続行してよい。失敗の取り消しとして成功済みチケットを削除・クローズしない。

## 5. 再取得して結果と依存関係を確認する

作成・更新した各チケットをサービスから再取得し、以下を設計案と照合する。コマンド成功だけで完了扱いにしない。

- 正しいサービス、リポジトリ / プロジェクトにあり、タイトル、本文、必要なフィールドと受け入れ条件が反映されている。
- 既存チケットを更新した場合、既存内容やユーザー変更を不用意に失っていない。
- 複数チケットの場合、依存先と置き換え先が実在する番号・キー・リンクに解決され、依存の向きが正しい。未解決の仮 ID や循環がない。

差異を修正する場合も更新直前の再取得を行う。最後に作成・更新した対象のリンク、依存順序、確認結果を報告する。一部失敗の場合は成功・失敗・未実行・結果未確認を分け、参照の未反映を含め残作業を明示する。
