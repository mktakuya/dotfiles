  - 連結して一塊となっている語（例: Webサイト、10px、1,000円）

## 思考・提案プロセス（BFS → DFS アプローチ）

設計・アーキテクチャに関わる議論や、複数のアプローチが考えられる課題に対して適用する。自明なタスク（typo 修正、単純なリファクタリング、明確に一択の実装など）ではこのプロセスを省略してよい。

ユーザーは「手堅く仕事を進める」ために、課題解決において**「幅優先探索（BFS）で合意してから、深さ優先探索（DFS）を行う」**ことを重視しています。コーディングエージェントは壁打ち相手として、以下のプロセスを強制・促進してください。

1. **幅優先探索 (BFS) フェーズ:**
   - すぐに単一の解決策の詳細やコード実装に入らないこと。
   - まずは必ず複数の解決策（案A, 案B, 案C...）を提示し、それぞれの Pros / Cons / 影響範囲 をフラットに比較する。
   - ユーザーが最初から1つの案に固執して深掘りしようとした場合、「詳細を詰める前に、他の選択肢も軽く洗い出しておきませんか？」と提案し、視野を広げるサポートをする。
2. **意思決定フェーズ:**
   - 複数の選択肢と Pros / Cons が出揃った段階で、「この状態でドキュメント（Notion等）にまとめ、チームに相談（壁打ち）しますか？」とユーザーに確認する。
3. **深さ優先探索 (DFS) フェーズ:**
   - チーム（またはユーザー自身）によって方針が1つに決定された後にのみ、詳細な設計、エッジケースの考慮、シーケンスの整理、具体的な実装コードの出力に移行する。

## ツール

### Git

- コミットメッセージは日本語で書き、件名は「〜する」のように動詞終わりにする
- コミットする前に `git-commit-convention` スキルを読み、件名・本文・Co-Authored-By の規約に従う

### Pull Request

- Pull Request は必ず**ドラフト**で作成し、レビュアーは自動でアサインしない
- 作成手順は `create-pull-request` スキルに従う

### コマンド

- GitHub に関する操作は gh コマンドを使う。`github.com` の URL を渡されたときも、直接アクセスせず gh コマンドで情報を取得する
- Jira に関する操作は acli コマンドを使う。`*.atlassian.net` の URL や Jira チケット ID（`ABC-123` のような `英大文字-数字` 形式）を渡されたときは `read-jira-workitem` スキルを呼ぶ
- Jira チケットの description を更新するときは `update-jira-workitem` スキルを使う

### MCP

- Notion・Figma・Slack の情報は、Web を検索せず MCP 経由で取得する
- ライブラリやフレームワークの API・設定を確認するときは context7 を使う
- 監視やエラーの調査は New Relic、CI の状態確認は CircleCI、データ抽出は Redash を使う
- Web アプリケーションの動作確認は Playwright MCP でブラウザを操作する
- ユーザーは JetBrains IDE を使っており、rails server や sidekiq、pnpm dev といった開発用サーバーはすでに起動済みである。エージェント自身が起動する必要はない

### 外部サービスの更新

- Notion ページや Jira チケットなど外部サービスのコンテンツを更新する前に、**必ず最新の内容を再取得する**。会話中に取得済みでも、ユーザーが手動で変更している可能性がある
- 手順の詳細は `external-service-edit` スキルに従う
